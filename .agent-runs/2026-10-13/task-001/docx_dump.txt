总述：这份规划书怎么用
它解决什么问题
《智能体业务场景需求说明书》回答「做什么、做到什么程度」；这份规划书回答「落到哪个文件、哪张表、哪个函数、按什么顺序做、做完怎么验」——它的目标是：把本场景的 P0 需求拆到半天粒度，使得编码 AI（或本人）拿到某一节就能直接开工，不需要再做设计决策。
每一条任务都带三样东西：产出物、前置依赖、验收命令。验收命令都是可以在本机直接跑出来的，不写「人工确认是否合理」这类无法执行的话。

落地顺序与依赖
总计划中三个场景串行，底盘在第 1~2 周一次建成，三个场景共用：
阶段 0（第 1~2 周）共用底盘与合规前置（三场景共用，不占本场景工期）：三层封装 + 场景配置化、离线安装包、三场景《规则判断书》、AI 使用声明模板、性能基线实测报告。没有 MS0 的基线数字，后面所有指标都无从验收。
阶段 1（第 3~8 周）场景二 新媒体（先行场景）：数据最全、难度中等、不依赖外部日历，先把「多智能体 + 合规卡点」骨架跑通。
阶段 2（第 9~13 周）场景一 数模（本场景）：素材真实但只覆盖一个题目，与竞赛窗口强绑定，且开赛后进入代码冻结，必须提前做完。
阶段 3（第 14~23 周）场景三 毕业论文：直接收益最高但见效周期最长、难度很高，放在最后。
顺序调整的唯一合法理由是外部窗口变化（如竞赛提前），此时本场景与场景二可对调；「底盘先行、人判卡点不省、达标线不放水」三条不变。

验收纪律
P0 不达标即不验收：A 类指标（有独立证据）不达标不验收；B 类（自证）需双人独立标注且 kappa ≥0.6 才有效；C 类（使用行为）不达标即暂停后续阶段，先改产品形态。
缓冲周只用于真值集冻结与人工评测，不得挪作开发；进度偏差优先砍 P1 保 P0，不允许通过放宽达标线来「追上进度」。

1.2 架构选型说明（参照 Agent 架构课程「7 大架构速览」）
本场景的 Agent 编排落在 7 号 Graph / Workflow 架构：Coordinator 是一张 StateGraph（状态 + 节点 + 边），4 个 LLM 角色是图上的 LLM 节点，确定性流水线（体检、执行、检查、出图）是确定性节点，人工卡点用人机回环（Human-in-the-loop）实现。选型理由与课程结论逐条对应：

[TABLE 5] rows=8 cols=3
候选架构 | 是否采用 | 理由（对应课程判断标准）
1 号 单 Agent | 不采用（仅作零件） | 单 Agent = bind_tools 后 invoke 一轮，无循环无记忆；本场景需要「生成→执行→检查→出图→写档案」多步闭环，单轮不够
2 号 ReAct | 采用（作为零件） | 每个 LLM 角色节点内部就是 Thought→Action→Observation 循环（检索卡片、调用工具），课程原话「1 号不是独立架构，而是所有东西的最小零件」
3 号 Plan & Execute | 部分借用 | 求解子问题先由 planner 出 3~4 个候选方案再执行，取其「先出结构化计划再施工」；但竞赛现场不允许图纸定死，计划必须可被体检结果推翻
4 号 Router + Skill | 不采用 | 本场景各角色不是「分类后各走各的、彼此不需要交流」——coder 的输入依赖 archivist 的档案与 planner 的方案，必须共享状态
5 号 Multi-Agent | 不采用（关键决策） | 单机 16 GB 内存做不到两个 8B 模型同时常驻做模型侧对抗，课程也提示 Multi-Agent 成本是单 Agent 数倍；数学判定权 100% 在人，不需要「辩论式」互相审查
6 号 Blackboard | 不采用 | 会诊型共享黑板适用于「多领域专家同时看彼此分析」；本场景角色职责边界清晰、串行依赖，共享状态由 SQLite 档案承担即可
7 号 Graph / Workflow | 采用（主架构） | 分支（体检结果走哪条路）、循环（修复 1 轮）、人工审批（口径确认卡点）、可审计可回溯，全部由图节点 + 条件边 + 检查点承担；课程结论「Graph 是终极万能架构，可复刻前面所有架构的能力」

人机回环的落地方式（参照课程「LangGraph 进阶_Human-in-the-loop」）：
口径冲突僵持、合理性检查 blocking、导出前合规校验三个节点调用 interrupt() 暂停图执行，保存完整状态（对应 SQLite WAL 事件表 + 档案版本），由人做出判定后以 Command(resume=...) 恢复，人的判定作为该节点的返回值落库。
检查点（checkpointer）用 SQLite 实现（对应课程 SqliteSaver 的本地方案）：进程崩溃后按事件表重建，恢复演练丢失版本 ≤1（NFR-5）。
与传统 ReAct 的对比正是课程列出的四大痛点：不能暂停（本场景需要人工卡点）、不能回滚（档案版本链 supersedes）、不能分支（体检/合理性条件边）、状态黑盒（每步写 event_log）。

system 要点：子问题类型 → 3 个候选方案；每个候选必须给「适用条件 / 样本量阈值 / 指标独立性要求 / 序列长度要求 / 实现难度 / 所需数据字段」；逐条对照体检摘要给出 satisfied: true/false 与理由；不得编造文献，引用只能来自 rag_search 返回的卡片（须带回 card_id）；检索必须通过工具调用，不得凭记忆。

{"type":"object","additionalProperties":false,"required":["subproblem_id","candidates","data_check","recommended_top2"], "properties":{"subproblem_id":{"type":"string"}, "candidates":{"type":"array","minItems":3,"maxItems":4,"items":{"type":"object",   "required":["name","why","sample_size_min","independence_required","series_len_min","difficulty","needed_fields","card_ids"],   "properties":{"name":{"type":"string"},"why":{"type":"string"},"sample_size_min":{"type":"integer"},   "independence_required":{"type":"boolean"},"series_len_min":{"type":["integer","null"]},   "difficulty":{"enum":["low","mid","high"]},"needed_fields":{"type":"array","items":{"type":"string"}},   "card_ids":{"type":"array","items":{"type":"string"}}}}}, "data_check":{"type":"array","items":{"type":"object","required":["candidate","requirement","satisfied","evidence"],   "properties":{"candidate":{"type":"string"},"requirement":{"type":"string"},   "satisfied":{"type":"boolean"},"evidence":{"type":"string","description":"档案字段路径或体检字段名"}}}}, "recommended_top2":{"type":"array","minItems":2,"maxItems":2,"items":{"type":"string"}}}}温度 0.3；输入 ≤5k、输出 ≤2.5k。调用预算 ≤3 次。
硬校验（Python，不靠 LLM）：recommended_top2 中任一候选在其 data_check 存在 satisfied=false → 计一次「明显错配」，验收要求全题集错配数 = 0，故 coordinator.py 在写入档案前拦截并要求重排。
失败规则：同 5.1；降级到 qwen3:4b 时只要求输出 candidates 与 data_check，recommended_top2 由 Python 按「全项 satisfied 优先、难度低优先」排序生成。
5.3 代码与出图 Agent（coder）
system 要点：只输出一个 Python 文件内容（允许代码围栏，base.py 会剥离）；必须 if name == "main":；禁止网络与子进程；只读 data/ 下输入、只写 results/ 与 figures/；必须在末尾调用 render_figures 的等价模板函数（由模板注入，不要自己重写绘图样式）；必须写 manifest.json，含 declared_outputs 列表；中文注释；不引入未在依赖清单中的包；matplotlib 只允许 Agg。
输出 JSON schema（外层包裹，便于程序化落盘）：
{"type":"object","additionalProperties":false,"required":["module","filename","purpose","declared_outputs","code"], "properties":{"module":{"enum":["prep","solve","sensitivity"]},"filename":{"type":"string","pattern":"^[a-z0-9_]+\\.py$"}, "purpose":{"type":"string"},"declared_outputs":{"type":"array","minItems":1,"items":{"type":"string"}}, "code":{"type":"string","minLength":50}, "figure_specs":{"type":"array","items":{"type":"object","required":["fig_id","title","chapter","seq"],   "properties":{"fig_id":{"type":"string"},"title":{"type":"string"},"chapter":{"type":"string"},"seq":{"type":"integer"}}}}}}温度 0.1；输入 ≤6k（档案字段子集 + 体检摘要 + 卡片要点，严禁把 6 张表原文塞进提示词）、输出 ≤2k。调用预算 ≤5 次（含 1 轮修复）。
失败规则：returncode != 0 或产出缺失 → repair_once 传入 stderr 末 40 行 + 原脚本，重生成 1 次（温度 0.0）；第 2 次仍失败 → Coordinator 判「连续失败 2 次」，降级 qwen3:4b 并把出图从脚本内联改为「两段式」（先出结果表，再由确定性模板 render.py 出图）；仍失败 → 转人工，写事件表 error_code='EXEC_FAILED'。
5.4 论文装配 Agent（assembler）
system 要点：只做结构装配——章节骨架、符号说明表、图表位、附录代码位、图题与编号；不得撰写摘要与论证段落；每段落属性必须标 origin: "agent" | "human" | "placeholder"；不得编造公式（公式只能来自档案 formulas[] 或标 TODO_HUMAN）。
输出 JSON schema：
{"type":"object","additionalProperties":false,"required":["sections","symbol_table","figure_slots","code_appendix"], "properties":{"sections":{"type":"array","minItems":5,"items":{"type":"object",   "required":["no","title","paragraphs"],"properties":{"no":{"type":"string"},"title":{"type":"string"},   "paragraphs":{"type":"array","items":{"type":"object","required":["origin","text"],     "properties":{"origin":{"enum":["agent","human","placeholder"]},"text":{"type":"string"},     "refs":{"type":"array","items":{"type":"string"}}}}}}}}, "symbol_table":{"type":"array","items":{"type":"object","required":["symbol","meaning","unit","source"],   "properties":{"symbol":{"type":"string"},"meaning":{"type":"string"},"unit":{"type":"string"},"source":{"type":"string"}}}}, "figure_slots":{"type":"array","items":{"type":"object","required":["fig_id","chapter","seq","caption","source_table"],   "properties":{"fig_id":{"type":"string"},"chapter":{"type":"string"},"seq":{"type":"integer"},   "caption":{"type":"string"},"source_table":{"type":"string"}}}}, "code_appendix":{"type":"array","items":{"type":"object","required":["path","caption"],   "properties":{"path":{"type":"string"},"caption":{"type":"string"}}}}}}温度 0.2；输入 ≤6k（档案 + 模板结构，不注入论文正文）、输出 ≤2k。调用预算 ≤3 次。

5.5 Coordinator 的仲裁环节（非 LLM 主体，单点 LLM 仅用于措辞）
定位：mmagent/agents/coordinator.py 是规则状态机，路由（阶段流转）、版本递增、人工卡点、失败计数、降级决策全部纯 Python 判定，不消耗调用额度。对应架构课程 7 号 Graph：节点 = 各角色与流水线，边 = 条件流转，人工卡点 = interrupt() 暂停 + Command(resume) 恢复。
唯一 LLM 使用点 arbitrate_conflict（prompts/coordinator_arbitrate.system.j2）：当 caliber_conflict 或档案字段出现两种口径僵持（final-1.md 2.3 ES-3）时，不做投票式仲裁，只输出「并行预研计划」——为 2~3 个候选各出一条最小验证指令。
system 要点：不得裁决谁对；只输出最小验证所需的「输入数据、脚本要点、可判定指标、预期耗时」；禁止引用外部文献。
输出 JSON schema：
{"type":"object","additionalProperties":false,"required":["topic","min_verifications","decision_rule"], "properties":{"topic":{"type":"string"}, "min_verifications":{"type":"array","minItems":2,"maxItems":3,"items":{"type":"object",   "required":["candidate","inputs","script_hints","judge_metric","est_minutes"],   "properties":{"candidate":{"type":"string"},"inputs":{"type":"array","items":{"type":"string"}},   "script_hints":{"type":"array","items":{"type":"string"}},"judge_metric":{"type":"string"},   "est_minutes":{"type":"integer"}}}},"decision_rule":{"type":"string","description":"由人执行的判定规则，不得由 Agent 执行"}}}温度 0.3；输入 ≤3k、输出 ≤1k。失败规则：失败即跳过，直接输出纯规则版预研计划（按候选名生成 3 条模板），不重试。

一、项目概述
1.1 项目背景
本计划书依据《何昆阳智能体业务场景需求分析》（定稿）编制。该需求分析面向三个来源于本人真实经历的 Agent 落地场景——数学建模竞赛协作、校园新媒体内容运营、数学毕业论文与文献助手，经「场景产品经理初稿 → 技术架构师评审 → 业务负责人评审 → 修订定稿」四轮 AI 协作评审形成定稿。
本计划书对应其中的场景一：数学建模竞赛协作。痛点来自本人 2024 年数学建模（校赛）A 题的真实经历：72 小时赛程里，最贵的故障不是「做不出来」，而是「安静地把错数字送进论文」——附件口径错误、量纲混用、图号与正文不一致，都不报错，直到评阅时刻才暴露。本场景要把可并行的检索、求解、作图、排版与进度管理交给 Agent，人专注建模判断。
三个场景并非三套互不相干的系统，而是共用同一套本地化技术底盘：Ollama 本地推理（qwen3.5 生成、qwen3-embedding 向量化）、ChromaDB 向量库、BM25 加 jieba 稀疏检索与 RRF 融合、SQLite 状态层，以及已在个人项目「企业级语义检索与 RAG 智能问答系统」中实现的重排、上下文压缩、Self-RAG 降级与流式输出等能力。本计划书的任务，就是把场景一的需求分析转化为可执行、可验收、可追溯的开发安排。
1.2 项目目标
总体目标：以一人可维护、零云支出、全本地推理为硬约束，在数模竞赛这一真实场景中落地「模型出候选、人做判定」的人机协同工作流，消灭本场景最贵的故障模式——口径错误（不报错、安静地把错数字送进论文），并把共用技术底盘沉淀为可复用的个人技术资产。

架构决策（沿用需求分析「三个不建议」）：
不为每个场景重写一套检索——三场景检索需求高度同构，抽一次共用底座，场景只做数据与工具适配；

3.2 架构选型说明（参照 Agent 架构课程）
本场景编排采用 7 号 Graph / Workflow 架构：Coordinator 为规则状态机（对应 StateGraph 的状态 + 节点 + 边），4 个 LLM 角色是图上节点，确定性流水线（体检、执行、合理性检查、出图）是确定性节点；每个 LLM 角色节点内部是 2 号 ReAct 循环（Thought→Action→Observation，检索卡片、调用工具）；方案生成借用 3 号 Plan & Execute 的「先出结构化计划再施工」，但计划必须可被体检结果推翻。
人机回环（Human-in-the-loop）落在三个卡点：口径冲突僵持、合理性检查 blocking、导出前合规校验——节点调用 interrupt() 暂停并保存完整状态（SQLite WAL 事件表 + 档案版本），人工判定后以 Command(resume) 恢复，人的判定作为节点返回值落库。检查点用 SQLite 实现，进程崩溃后按事件表重建，恢复演练丢失版本 ≤1。
不采用 5 号 Multi-Agent 辩论式的关键理由：单机 16 GB 内存做不到两个 8B 模型同时常驻做模型侧对抗；数学判定权 100% 在人，不需要「互相审查」的辩论结构。课程结论与本场景约束一致：Graph 是终极万能架构，可复刻前面所有架构的能力，且分支、循环、人工审批、可审计全部原生支持。

六、质量保证计划
6.1 评估体系
沿用需求分析的三类指标划分，不合并总分掩盖短板：
A 类（有独立证据，验收门槛）：锚点格式与正确率、机器耗时、误报预算、排版检查、检索时延、云支出、运行期外发请求数等——不达标即不验收；
B 类（自证，仅参考值）：卡片矛盾率、定义/定理召回率、符号表质量、候选非噪声率等——需双人独立标注并报 kappa（≥0.6 才有效）或隔 2 周盲评；
C 类（使用行为，P0 门槛）——不达标即暂停后续阶段，先改产品形态。
达标线与观察值分离：每场只产出 1 个样本的比率类指标只记录数值，不作为当轮验收依据。
6.2 测试与回归策略

[TABLE 11] rows=8 cols=3
测试类型 | 范围 | 要求
Golden file 回归 | 解析、切分、编号检查、锚点校验四模块 | 各一组，不设覆盖率门禁
A 题回归 | 本场景代码生成与出图 | 冻结环境 ≥50 次，首次可运行率 ≥70%
合规回归 | 120 条测试集（高危 ≥40，三场景共用） | 固化为 tests/compliance_cases.yaml；高危漏检 ≤1
检索回归 | 20 条基准查询（中英各 10） | Recall@10 ≥80%
人工评测 | 各达标线指标 | 每周固定半天额度；双人独立标注加 kappa；真值集先冻结再跑
可用性测试 | 本场景 NFR-6 | 未读文档新用户 ≤5 步、≤15 min，3 人各测 1 次、3/3 通过
恢复演练 | 事件表重建 + kill 重启 | 丢失版本 ≤1

6.3 需求追溯
每条 FR/NFR 的阶段归属与验收标准在需求分析中已定义，并在《场景一 实施规划书》第 8 节落为「需求编号 → 交付物 → 测试用例」三级对应；开发中以该表为准，未对应到测试的 P0 需求不得关闭。范围变更遵循同一纪律：新增需求须补优先级判据（省下的人时 ÷ 开发成本 ÷ 出错代价），并写入项目日志。

7.2 升级与止损机制
场景一：任一步骤连续失败 2 次，Coordinator 换更小模型或降需求并入档；赛后代码冻结前完成复盘；
共性：进度偏差优先砍 P1 保 P0；缓冲周专用于真值集冻结与人工评测，不挪作开发。
